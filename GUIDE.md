# Developer Guide

This guide explains what's actually deployable from this repository, how it's configured, and what a new contributor needs to understand before touching it. It's based only on what's present in the repo — there is no Dart/Flutter source code here, so anything about internal app logic is out of scope for what can be honestly documented from this repo alone.

## 1. What this repo is (and isn't)

- **Is:** the static output of a Flutter web build (`flutter build web`) for an app called `admin` / "ScrapifyAdmin".
- **Isn't:** a Node/JavaScript project (no `package.json`), and isn't the Flutter source project either (no `pubspec.yaml`, no `lib/`). You cannot run `flutter run`, `flutter pub get`, or edit any `.dart` file from this checkout — those files simply aren't here.
- The two commits in `git log` (`Add files via upload`) confirm this was populated by dragging a build folder into GitHub's web UI, not by CI/CD.

If you need to change how the app behaves, you need the original Flutter project (the one with `pubspec.yaml` and `lib/main.dart`) — this repo is a deploy target for its `build/web` output, not the project itself.

## 2. Configuration: how the app talks to its backend

The app is wired to a specific Firebase project. This is set in two places:

**`index.html`** loads the Firebase JS SDK and initializes it with an inline config object:

```html
<script src="https://www.gstatic.com/firebasejs/9.14.0/firebase-app.js"></script>
<script src="https://www.gstatic.com/firebasejs/9.14.0/firebase-analytics.js"></script>
<script>
  const firebaseConfig = {
    apiKey: "...",
    authDomain: "scrapify-8e990.firebaseapp.com",
    databaseURL: "https://scrapify-8e990-default-rtdb.firebaseio.com",
    projectId: "scrapify-8e990",
    storageBucket: "scrapify-8e990.appspot.com",
    messagingSenderId: "...",
    appId: "...",
    measurementId: "..."
  };
  const app = initializeApp(firebaseConfig);
  const analytics = getAnalytics(app);
</script>
```

This only wires up **Firebase Analytics** for the page shell. The rest of the app's Firebase usage (Auth, Firestore, Realtime Database, Storage — all present per `assets/NOTICES`) is compiled into `main.dart.js` and initialized from the Flutter/Dart side using the Flutter `firebase_core` plugin, which on web reads the same kind of config. That configuration lives in the original Dart source (typically a `firebase_options.dart` generated by the FlutterFire CLI), which is not part of this repo.

**Security note for new contributors:** Firebase web config values (API key, project ID, etc.) are not secrets in the traditional sense — Google's model expects them to be public in client bundles, exactly as they are here. Actual access control is enforced by Firestore/Realtime Database/Storage **security rules** on the Firebase project itself, not by hiding this config. If you're auditing this app, look at the security rules in the Firebase console for the `scrapify-8e990` project, not at whether the config is visible client-side.

There are no `.env` files, no `firebase.json`/`.firebaserc`, and no other config files in this repo — all runtime configuration the build needs is embedded in `index.html` and inside the compiled `main.dart.js`.

## 3. How the pieces fit together at runtime

1. Browser requests `index.html`.
2. `index.html` shows a plain CSS/HTML "LOADING" splash, then loads the Firebase Analytics SDK and initializes it against the `scrapify-8e990` project.
3. `flutter.js` bootstraps the Flutter web engine and loads `main.dart.js` (the compiled app) plus the CanvasKit WebAssembly renderer from `canvaskit/`.
4. Once Flutter renders its first frame, the page registers `flutter_service_worker.js`, which caches all files listed in its `RESOURCES` map (everything under `assets/`, plus the core JS/wasm files) so the app can reload quickly and work as an installable PWA (see `manifest.json`).
5. Inside the compiled app, Firebase Auth/Firestore/Realtime Database/Storage clients (bundled per `assets/NOTICES`) handle sign-in and data access directly against the same `scrapify-8e990` Firebase project — there is no custom backend server or REST API in this repo for the app to call. (This is why no `API_REFERENCE.md` is included: there are no application-defined HTTP routes/controllers anywhere in this repository — the app is a Firebase client, not an API server.)

## 4. Updating this deployment

Since there's no source here to edit:

1. Make your changes in the actual Flutter project (elsewhere).
2. Run `flutter build web` there.
3. Copy the resulting `build/web/*` contents over this repository's files (they map 1:1 — `index.html`, `main.dart.js`, `assets/`, `canvaskit/`, etc.).
4. Commit and push/redeploy.

## 5. Things to double check before relying on this build

- `version.json` reports `version 1.0.0`, `build_number 1` — there's no visible versioning scheme beyond this single value, so don't assume this build is current without checking the source project it was generated from.
- The bundled `twilio_flutter` package implies some SMS/telephony feature exists in the app, but which screen uses it, and how Twilio credentials are supplied, is defined in the Dart source, not here.
- Because `main.dart.js` is minified/tree-shaken JavaScript output of `dart2js`, it is not practical (or reliable) to reverse-engineer specific screen behavior from it — treat the feature list in `README.md` as inferred from bundled assets/packages, not as an exhaustive functional spec.
